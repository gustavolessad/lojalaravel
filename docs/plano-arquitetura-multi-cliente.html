Plano: Arquitetura Escalável Multi-Cliente

Loja Virtual Laravel — Planejamento estratégico para replicação em múltiplos clientes

Data: 28/02/2026    Status: Planejado — aguardando implementação

Contexto e Objetivos

O sistema de loja virtual está em desenvolvimento e será replicado para múltiplos clientes, cada um com site e banco de dados próprios. A arquitetura precisa atender a:

  • Atualizações do core chegando a todos os clientes com facilidade (um único comando)
  • Módulos opcionais (ex: integração Bling, WhatsApp) como pacotes Composer separados
  • 2 templates visuais padrão + painel de aparência completo no admin
  • Override de views por cliente quando necessário (sem modificar o core)

Satis — Servidor Composer Privado

O Satis é uma aplicação PHP gratuita que cria um repositório Composer privado. Cada cliente aponta para https://packages.empresa.com.br no composer.json e instala os pacotes privados normalmente como se fossem do Packagist.

Custo: apenas hospedagem (pode ser GitHub Pages = gratuito).

Estrutura do loja-cliente-template

empresa/loja-cliente-template/
├── composer.json       → require: empresa/loja-core
├── .env.example        → todas as variáveis necessárias documentadas
├── bootstrap/
├── public/
├── storage/
└── deploy.sh           → script de atualização automatizada

Fluxo de novo cliente

git clone empresa/loja-cliente-template meu-cliente
cd meu-cliente && cp .env.example .env
# Preencher DB, APP_URL, ASAAS_TOKEN, etc.
composer install
php artisan key:generate
php artisan migrate --seed
php artisan storage:link

Fluxo de atualização (quando o core recebe melhorias)

composer update empresa/loja-core
php artisan migrate --force
php artisan config:cache && php artisan view:clear

Esse script pode ser automatizado via CI/CD (GitHub Actions) para rodar em todos os clientes automaticamente.

Fluxo de adição de módulo

composer require empresa/module-bling
php artisan migrate --force
# Configurar no Admin: Aplicativos > Bling > Configurações

Parte 2 — Sistema de Templates (2 templates)

Estrutura de Views

resources/views/
  themes/
    default/                   ← Template 1: "Padrão" — moderno e clean
      layouts/shop.blade.php
      layouts/account.blade.php
      layouts/auth.blade.php
      shop/                    (category, product, checkout, brand...)
      account/                 (auth, dashboard, addresses, orders, profile, returns)
      livewire/shop/
      livewire/account/
      components/
      theme.json               ← { "name": "Padrão", "description": "Layout moderno e clean" }
    compact/                   ← Template 2: "Compacto" — layout mais denso
      layouts/shop.blade.php   (apenas os arquivos que diferem do default)
      theme.json               ← { "name": "Compacto", "description": "Layout compacto" }
Lógica de override (prioridade de resolução, maior → menor):
  1. resources/views/ (raiz do projeto do cliente) — customização própria
  2. resources/views/themes/{tema-ativo}/ — template escolhido no admin
  3. resources/views/themes/default/ — fallback
  4. Vendor views (pacotes Composer)

Exemplo: cliente quer apenas mudar a homepage → cria resources/views/welcome.blade.php e só essa view é sobrescrita.

Mecanismo de Resolução (AppServiceProvider)

// Em AppServiceProvider::boot()
$theme = Setting::get('appearance_theme', 'default');
view()->addLocation(resource_path("views/themes/{$theme}"));
view()->addLocation(resource_path("views/themes/default")); // fallback

CSS Variables — Cores Dinâmicas

As cores são injetadas como variáveis CSS no <head> do layout. Não exige recompilar o Tailwind — muda instantaneamente ao salvar no admin.

@php
    $primary   = Setting::get('appearance_primary_color', '#111827');
    $secondary = Setting::get('appearance_secondary_color', '#f59e0b');
    $font      = Setting::get('appearance_body_font', 'Inter');
@endphp
<style>
    :root {
        --color-primary: {{ $primary }};
        --color-secondary: {{ $secondary }};
        --font-body: '{{ $font }}', sans-serif;
    }
</style>

tailwind.config.js — adicionar colors dinâmicas:

colors: {
    brand:  'var(--color-primary)',
    accent: 'var(--color-secondary)',
}
// Usar bg-brand, text-brand, border-accent nos templates

Parte 4 — Sistema de Módulos

Dois tipos de módulo

TipoExemplosComo instalar

config/modules.php (novo arquivo)

return [
    // Módulos internos (sempre instalados no core)
    'internal' => [
        'newsletter'         => env('MODULE_NEWSLETTER', true),
        'stock_notification' => env('MODULE_STOCK_NOTIFICATION', true),
        'returns'            => env('MODULE_RETURNS', true),
    ],
    // Módulos externos (preenchido pelos ServiceProviders instalados)
    'external' => [],
];

app/Support/ModuleRegistry.php (novo)

Singleton que os módulos externos usam no ServiceProvider::boot() para se registrar:

class ModuleRegistry {
    protected array $modules = [];
    public function register(array $meta): void { ... }
    public function all(): array { ... }
    public function isInstalled(string $id): bool { ... }
}

Filament Page: Aplicativos

Local: Admin > Configurações > Aplicativos
Exibe:
  • Módulos internos com toggle ativo/inativo (grava em Setting)
  • Módulos externos instalados: cards com nome, versão, link para configurações
  • Módulos externos disponíveis (lista curada): instrução composer require
